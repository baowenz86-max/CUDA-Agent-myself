研究背景与目标 Background & Goal

问题：为什么需要反编译？

  • GPU 张量程序经编译器优化后生成 SASS/PTX
  • 低层表示丢失变量名、控制结构、数据类型等高级语义
  • 现有工具（nvdisasm）仅能做指令级翻译，不可读
  • 阻碍调试、安全审计、性能分析与知识迁移

瓶颈：缺少训练和评估数据

  • LLM 在代码翻译任务上展现潜力
  • 但 SASS→CUDA 反编译缺少对齐数据
  • 不像正向编译有编译器保证正确性
  • Ground truth 必须自动生成并验证

本阶段目标

  • 构建 Agent 驱动的自动化管线，批量生产「可信 CUDA 源码 ↔ SASS/PTX」配对数据
  • 任务定义：输入 = 优化后的 SASS/PTX，输出 = 功能等价的可读 CUDA C++ kernel
  • 当前聚焦上游（配对数据生产），为中游（反编译模型训练/评估）提供基础

反编译配对数据的设计需求 Data Requirements

GT 可靠性

CUDA 源码必须通过编译 + 功能验证，杜绝错误 ground truth 毒害训练

低层真实性

SASS/PTX 由真实编译器（nvcc/cuobjdump）生成，非手写汇编

语义对齐

一条 CUDA 对应一条 SASS，功能完全等价，反编译本质是语义恢复

任务多样性

覆盖向量运算、矩阵运算、归约、访存模式、线程协作等

复杂度梯度

单算子 → 多算子融合 → 含共享内存与同步的多 kernel 程序

可验证性

保留参考实现与测试用例（契约），支持反编译结果的自动验证

防泄漏

训练集与测试集程序 AST 相似度 < 0.9，避免评估虚高

可复现性

记录工具链版本、编译参数与运行环境，样本可追溯可重放
设计决策：采用「先生成可信 CUDA → 再编译出 SASS」的正向路径，完整保留 GT 与验证 oracle

关键技术细节 Key Techniques

参考契约机制

  • 固定 seed 运行参考 PyTorch 模型
  • 采集每步 shape / dtype / stride
  • 记录逐语句中间检查点
  • 为 LLM 提供「不执行就能推理」的依据
  • 同时保留验证反编译结果的 oracle
  • 无法插桩的控制流明确标记
  • 契约仅诊断用，不替代正式验证

结构化修复循环

  • 输入：失败证据 + 契约 + 历史候选
  • LLM 输出 JSON 根因假设（hypothesis + evidence）
  • 文件级变更（files + delete_files）
  • 安全检查 → 编译 → 验证 → 评分
  • 排序：通过数 > 失败阶段 > 误差 > 时间
  • 退化检测 + 自动回退历史最优
  • ≤3 轮 × 3 候选，平衡深度与成本

三阶段生成 + 约束

  • Stage 1：Python 接口 model_new.py
  • Stage 2：CUDA kernel custom_ops.cu
  • Stage 3：pybind 绑定 *_binding.cpp
  • .cu 禁止 torch / ATen / c10 依赖
  • .cpp 禁止 kernel launch 语法
  • 职责分离降低单次生成复杂度
  • 写入前路径白名单 + 内容检查

六层数据质量门禁 Quality Gates

L1 接口合规

写入前路径白名单 + 内容检查 → 生成代码不越界

L2 可编译性

nvcc 编译 + Ninja 增量构建 → 语法正确

L3 功能正确性

5 次不同 seed 验证 + 数值比对 → 语义等价（核心）

L4 诊断定位

checkpoint 级错误定位（debug_forward）→ 修复有据可依

L5 可复现性

固定 seed + 环境版本记录 → 结果可重现

L6 可追溯性

每候选完整快照 + API 调用日志 → 问题可回溯
⚠ 编译成功 ≠ 功能正确 L2 仅证明语法合法，L3 才是语义等价的保障。所有进入 Phase 2 的代码均已通过 L3。

样本展示：Task #0006 ReflectionPad2d + ge + remainder

Agent 生成的 CUDA Kernel（ground truth）

__global__ void ge_scalar_kernel( const float* input, float* output, float scalar, int n) { int idx = blockIdx.x * blockDim.x + threadIdx.x; int stride = blockDim.x * gridDim.x; for (int i = idx; i < n; i += stride) { output[i] = (input[i] >= scalar) ? 1.0f : 0.0f; } } void ge_scalar_launcher(const float* input, float* output, float scalar, int n, cudaStream_t stream) { int threads = 256; int blocks = min((n + threads - 1) / threads, 65535); ge_scalar_kernel<<<blocks, threads, 0, stream>>>( input, output, scalar, n); }

对应的 SASS（nvcc 生成，sm_90）

/* ge_scalar_kernel — 反编译输入端 */ MOV R0, SR_TID.X; // threadIdx.x MOV R1, SR_NTID.X; // blockDim.x MOV R2, SR_NCTAID.X; // blockIdx.x IMAD R0, R2, R1, R0; // idx MOV R3, c[0x0][0x168]; // n ISETP.GE.AND P0, PT, R0, R3, PT; @P0 EXIT; // 边界检查 LDG.E.SYS R4, [R0+input]; // 全局加载 SETP.GE.F32 P1, PT, R4, scalar; SEL R5, 1.0, 0.0, P1; // 三元选择 STG.E.SYS [R0+output], R5; // 全局存储
左侧为 Agent 生成的可读 CUDA（ground truth），右侧为 nvcc 编译产生的 SASS（反编译输入）。两者功能完全等价，已通过 5 次不同 seed 验证。

当前问题与局限 Limitations

数据规模不足

32 条仅够 few-shot 评估，不够微调训练
→ 计划扩展到 200+ 条

单一 GPU 架构

目前只有 sm_90 的 SASS，缺少跨架构变体
→ 增加 sm_80 / sm_89 等多架构编译

验证覆盖有限

5 次固定 seed 不能覆盖所有边界情况
→ 增加属性测试与边界值测试

算子类型集中

以 3 算子组合为主，缺少更复杂融合模式
→ 扩充 Ops-6K 采样策略

反编译可行性未验证

配对数据能否用于训练/评估反编译模型尚无实验证据
→ 下一步 zero-shot 基线实验
